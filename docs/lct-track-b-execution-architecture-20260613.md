# Track B 执行架构：选型裁决与开工计划（质询轮 + stats）

- 日期：2026-06-13
- 状态：已裁决，待开工
- 上游：`docs/lct-debate-stats-architecture-20260611.md`（深化设计，全文继续有效，本文档不复述其内容）、ADR-0002、ADR-0003
- 性质：本文档回答三件事——①为什么是这两个功能（需求本质）；②候选方案与裁决依据；③ACP 转正（M7，2026-06-12）之后深化设计需要补的环境差量与开工顺序。

---

## 1. 需求本质（第一性原理重述）

- **B-1a 质询轮**：Stage 2 的批评是未经检验的单方证词——评审说"Response B 算错了"，这句话本身可能是错的，而主席没有第二信源分辨"批评成立"还是"批评跑偏"。需求 = 给主席提供**经过对抗检验的批评**；同时满足项目立项动机"模型对线出真知"。
- **B-2 stats**：每次 run 的 Stage 2 都在生产"谁给谁排第几"的互评数据，已付费、躺在 manifest 里无人使用。需求 = 把存量数据变成**模型阵容决策依据**（谁该当成员、谁该当主席）。

## 2. 候选方案与裁决

### 2.1 B-1a：三案对比，裁决方案 A

| 方案 | 内容 | 裁决 |
|---|---|---|
| **A 质询轮**（固定一轮 Stage 2.5） | 成员看到针对自己的匿名批评，写回应；主席拿"批评＋辩护"综合 | **采纳**。唯一引入新信息的方案——辩护方持有评审没有的上下文。代价：+N 次调用、约 +1 阶段墙钟（M6 口径预估总耗时 +30~50%） |
| B 主席裁决（零新调用） | 不加轮次，Stage 3 prompt 要求主席逐条核验批评并标注采信/驳回 | **保底退路**。零成本零延迟，但无新信息，法官兼任辩护律师。若 A 触发推翻条件（答辩普遍无增量），退到 B |
| C 定向质询（只让被实质批评者答辩） | 调用数省约一半 | **否决**。"什么算实质性批评"的判定本身是新的出错点与边界负担，省下的调用费不抵引入的内部复杂度；与红线（不为省成本牺牲交互完整性）冲突 |

### 2.2 B-2：三案对比，裁决方案 A

| 方案 | 内容 | 裁决 |
|---|---|---|
| **A stats 命令**（只读聚合历史 manifest） | 跨 run 互评统计：常居前位率、打分松紧、剔自评、归一化位次、不造综合分 | **采纳**。被动遥测是该需求的成本下界：数据是历史 run 白送的，统计纯本地零调用 |
| B 主动 benchmark 子系统（固定题库定期评测） | 标准化成绩单 | **否决**。每次评测烧真实模型调用＋维护题库新资产；使用场景是日常决策辅助，A 的"自然实验"数据免费且持续增长。若 A 暴露历史数据太稀（阵容单一无可比性），再考虑 B 的小题库补采样 |
| C 一次性分析脚本（不进产品） | 用时手跑 | **否决**。manifest 格式知识散落产品外，格式演进即 silent 错；对 PM 用户"维护野生脚本"是负资产 |

### 2.3 选型方法论说明

外部 skill 调研结论（2026-06-13，EveryInc/compound-engineering-plugin 与 mattpocock/skills 两仓库逐项评估）：无适配"为成熟项目起草功能架构文档 + 六字段 ADR"的 skill，按项目既有 ADR 惯例与 CLAUDE.md 架构纪律直接起草。唯一吸收的外部思路：mattpocock ADR-FORMAT 的"何时值得写 ADR"三门槛（难以撤销＋不解释会困惑＋真实权衡结果）——Track B 选型同时满足三条，故立 ADR-0003。

## 3. ACP 转正后的环境差量（深化设计的三处补丁）

`docs/lct-debate-stats-architecture-20260611.md` 写于 ACP 转正（M7）之前，以下三处按新环境读：

1. **默认 backend 已是 acp**（main @ `9abb2d1`）。原文 §1.5"direct 与未来 ACP 命名规则沿用各自 runtime helpers"中"未来"二字作废——Stage 2.5 的 rebuttal 调用走 `provider.query_model()`（M3 签名门卫保证双 runtime 同签名），默认即产生 `*.acp.transcript.jsonl` 证据链。
2. **stage2_5 记录进 M4 防伪门**：rebuttal 的 ModelCallResult meta 携带与 Stage 1/2/3 相同的 44 键契约（含 7 个 ACP evidence 字段）；manifest `stages.stage2_5[]` 声明 ACP 时，validate 交叉触发门必须覆盖该 stage——这是 B1 任务卡的显式集成点与契约测试项，不是自动免费获得的。
3. **验收必须双 runtime**：B1 的 debate-on golden 用 direct 注入路径保确定性（与现 golden 哲学一致）；live E2E 走默认 acp。`--runtime-backend direct` 回退路径上 debate 必须同样完整工作（一条契约测试 + 一次 direct smoke）。

stats（B-2）为纯只读聚合，backend 无关；唯一交点：`RunFacts` 采集对 `runtime_backend` 字段如实透传（报告可按 backend 切片），不做任何 backend 推断。

## 4. 里程碑与流程

沿用 ACP 线已验证的流水线：任务卡 → 隔离 worktree → 执行 Agent 红绿 TDD → 架构师独立复核 → ff-only 合并 → 推送前 subagent 卫生 review。

| 里程碑 | 内容 | 先后依据 |
|---|---|---|
| **B1 质询轮** | 深化设计 §1 全单 + 本文档 §3 差量；任务卡另出 | 先做：动 council 主流程（Stage 3 prompt、manifest、validate、HTML），风险高者先行 |
| **B2 stats** | 深化设计 §2 全单；任务卡另出 | 后做，与 B1 无依赖，可在 B1 review 期间并行开工 |

- 回滚锚：B1 合并前打 `pre-track-b1`，B2 合并前打 `pre-track-b2`。
- golden 纪律延续：debate 未启用时全链路与现行为逐字节一致（`--debate` 是显式 opt-in，默认体验零变化）；stats 是新增子命令，不触碰既有 golden。
- `EXPECTED_META_KEYS` 44 键预期不变（rebuttal 调用复用既有 meta 契约；若执行中发现必须扩列，停下来回报，不得静默扩）。
