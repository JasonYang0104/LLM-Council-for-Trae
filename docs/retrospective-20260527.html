发现的问题

P0 traecli runtime 大面积不稳定

现象：8 模型并发时，Q2 黑客松技术栈 7/8 返回 traecli result error，连 GLM-5.1 和 Kimi-K2.6 也失败。降低到 3 模型后才跑通。

根因：traecli 内部并发处理存在资源竞争或连接池耗尽。并发 8 个进程时大部分返回 result error；DeepSeek-V4-Pro 和 Qwen3.6-Plus 偶发 Go 侧 segfault（conf.go:141 的 RealName 空指针）。

建议：

  • 短期：在 TraeCliProvider 中引入并发控制 semaphore，默认 concurrency=3
  • 中期：对 traecli result error 自动重试 1 次（间隔 10s），区分 runtime 偶发崩溃 vs 模型本身不行
  • 长期：向 traecli 团队反馈 segfault bug，推动修复

P1 模型稳定性梯队明确，roster 策略未跟上

P1 meta.json 中 tool_calls_count 缺失

现象：本轮 E2E 所有 stage1 的 meta.json 中 tool_calls_count 和 turns_count 未写入，HTML 模型表现摘要显示为 —。

建议：在 stage1_collect_responses 中对每个 call_result 调用 write_json(meta_path, call.to_json())，同步修复 stage2/stage3。

P2 degraded_ok 状态下 CLI 退出码为 1

现象：Q1 返回 degraded_ok 但 CLI 退出码为 1，调用方误以为完全失败。

建议：degraded_ok 返回退出码 0（或新增退出码 2 供脚本区分），JSON 输出中标注 degraded: true。

P2 chairman 兼任 member 时 quorum 逻辑过严

现象：8 成员 roster 中 chairman 也是 member，排除 chairman 后 7 个非主席需至少 6 个 ok，容错空间仅 1 个。

建议：区分 chairman 独立 vs 兼任 member 两种场景——兼任时其 stage1 ok 应计入 quorum，但 chairman 角色的失败不触发 stage1 失败。
