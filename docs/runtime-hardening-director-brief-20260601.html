Runtime Hardening Director Brief

LCT 已经从“做出一个可运行的本地 council CLI”进入“把 runtime 打磨到可靠可用”的阶段。现在最值得投入的，不是继续堆新能力，而是把运行期的并发、超时、退出、降级和状态语义治理清楚。

日期：2026-06-01

为什么现在做

入口问题已经基本解决。另一个 workspace 的效果测试说明，用户能够从根目录能力直接触发 LCT；真正暴露出来的短板，已经不是“不会用”，而是“运行时在复杂场景下不够稳”。

这轮迭代的触发证据不在当前 repo，而在测试 workspace：
/Users/bytedance/Documents/AI Coder/test/LLM-Council-for-Trae/.trae/postmortem/2026-06-01-lct-run-failure.md

那份复盘的价值不在某次 run 失败本身，而在于它明确指出了运行期的系统性问题：多个 run 并发争抢同一批模型资源、Stage 2 缺少超时闭环、chairman_timeout 暴露给用户却未真实生效、中断退出后的清理不够稳，以及 Stage 3 失败后缺少足够体面的降级收场。

阶段判断

这条线现在最合理的节奏不是补丁式修 bug，而是分层治理 runtime。顺序应该保持简单而稳定：

  • P0 防自爆：并发互斥、Stage 2 超时、进程清理。
  • P1 说真话：timeout 真值源、错误分类、状态机一致性。
  • P2 可收场：Stage 3 降级输出、更可信的恢复与收尾。
  • P3 数据化优化：重试退避、回归套件、运行画像与后续调参。

策略主线

并发控制不建议用一个粗暴的大锁一把梭。更合适的方向是三层控制：run lease 负责标识某个 run 的生命周期，global slot lease 限制同时活跃的 live 模型查询数，model lease 则限制同一模型在同一时刻只被一个 live query 占用。

这样一来，LCT 不是简单地“禁止并发”，而是在保留合理并行度的同时，把真正稀缺的资源约束起来，避免多个 run 同时争抢同一个模型，把成功率打穿。

推进方式

这条线适合用长线程推进，而不是短平快地修一两个点。推荐和 subagent-lead 一起工作，以 tdd 为主线；先把设计方案和测试方案沉淀清楚，再开始实现。实现责任以“测试最终都通过”为准，而不是以“功能先写出来”为准。

实现过程中持续维护 notes.md，记录那些规范里没写、但实现时不得不做出的判断、改动和权衡。这样下一会话接手时，看到的不只是 diff，还能理解背后的取舍。
