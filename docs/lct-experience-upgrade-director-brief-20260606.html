结论

LCT 已经可用，当前要解决的是用户理解、控制和信任结果的体验问题。最终文档把这次升级限定为体验增强，不是 runtime 重写，也不是模型 benchmark。

架构师任务文档位于 docs/lct-experience-upgrade-architect-brief-20260606.md。它已经补入现有 artifact 结构、责任边界、输入判定矩阵、模型裁剪规则、主席贡献说明可信标准和回归测试。

为什么要做

当前 HTML 顶部展示 Quorum 状态 4 / 3 · normal quorum，工程上可解释，但用户不需要在第一眼看到 quorum 阈值。用户需要看到的是参与最终结果的成员模型。

主席综述也存在透明度问题：用户难以判断最终答案中哪些观点来自哪些模型、哪些是共识、哪些是主席新增判断。这需要更强的 provenance，但不能伪造成精确贡献百分比。

过程

  1. 还原当前 LCT 事实：三阶段 council、validate 门槛、默认 4 成员、最低 3 个有效成员、HTML 确定性导出。
  2. 写出架构师任务文档第一版，覆盖 HTML 简化、主席贡献说明、输入改造、用户自选模型四个体验需求。
  3. 让白纸 subagent 审查文档清晰度，不做实现方案。
  4. 根据审查反馈补齐 artifact 样例、责任边界、判定矩阵、模型优先级、失败行为和测试标准。

不在 summary card 展示 Quorum 状态、4 / 3、normal quorum、有效成员：。底层 quorum 证据仍保留。

主席贡献说明

不建议输出精确比例。建议用“共识观点、主要采纳、分歧处理、主席新增、未明显采用”这类可审计表达，并校验引用的 Response label 和 model 是否真实存在。

输入改造

默认 raw。只有用户明确要求意图理解、架构评估、结构化或 fact pack 时，才允许 structured。即使 structured，也必须保留 Original input，并排除 operator envelope。

用户自选模型

默认不问。只有用户表达模型选择意图时才触发。最终 members/chairman 必须来自当前 traecli models --json。members 最多 4 个，产品路径要求至少 3 个 candidates。超过 4 个时按 LCT 成员优先级裁剪。

风险

  • 贡献说明如果无证据，会变成假透明。
  • AskUserQuestionTool 如果成为 core 依赖，会破坏 CLI 和其他宿主环境。
  • 模型自选如果不受当前模型清单约束，会破坏 expected/actual model 校验。
  • 输入改造如果过宽，会重现 Agent 悄悄改写用户问题的问题。
  • HTML 简化如果误删 quorum/backfill/search 证据，会削弱可复盘性。

建议推进

不要一次性塞进一个大 PR。建议按三阶段推进：低风险展示与 Skill 规则、模型选择交互产品化、主席贡献说明。每一阶段都应有独立测试，并保留 compileall、make test、git diff --check 的回归门槛。

当前完成的是评估输入，不是实现。下一步可以把架构师 brief 交给架构评审，要求其给出正式架构建议、风险和分阶段实施路线。
