LCT Input Boundary Docs

Branch: codex/lct-input-boundary-docs-20260604 · Scope: docs / Skill / tests

本轮把 LCT 的输入边界写成了可测试的文档合同：_lct_question.md 只承载 council 成员要回答的问题、必要事实背景、输出要求和 Report topic；外层 Agent 的运行职责留在外层。

为什么做

v9 E2E 暴露的问题不是 runtime 坏了，而是调用说明含糊。前两次 run 把“维护 notes.md”这类外层执行要求带进了成员可见输入，成员模型把它当成自己的任务，尝试文件工具后触发 tool contamination。

第三次用更窄的 council-only input 和 answer_only 通过，但这只能证明收窄输入有效，不能证明默认工具模式应该改成 answer_only。真正的修复点是 Skill 和 README。

改了什么

  • README quickstart 明确 _lct_question.md 只写 council-facing 问题、必要事实背景、输出要求和 Report topic。
  • canonical Skill 和 .trae Skill 同步区分 council input 与 operator envelope。
  • notes.md 被限定为外层 Agent 维护，不要求 council 成员创建、读取、修改或维护。
  • fact pack 被限定为可选、直接嵌入、必须标注来源、只包含事实背景和来源、不能包含执行指令。
  • 新增文档契约测试覆盖输入边界、raw input 默认、fact pack、notes 和工具模式判断权。

没改什么

Runtime

不改 runtime、不改 validate、不新增 CLI input classifier。

Tool Mode

不改 --member-tool-mode 默认值，不强制 answer_only，不强制外层搜索。

产品口径

默认保留用户原始实质问题。只有用户明确要求思考真实意图、拆解问题、重构输入、加入事实包或结构化输出时，外层 Agent 才使用 structured by Agent，并且必须保留 Original input。

搜索和工具模式保持由外层 Agent 判断。汇报必须继续拆开 lct_search_allowed、lct_search_used 和 agent_external_search_used。

验证证据

TDD 红灯：新增测试后旧口径失败，22 个测试中 10 个 subtest 失败，集中在工具模式判断权、.trae Skill 输入边界和 canonical Skill 默认 structured by Agent。

PYTHONPATH=src python3 -m unittest tests.test_global_install_skill_docs
PYTHONPATH=src python3 -m compileall src
make test
git diff --check main..HEAD

绿灯结果：目标测试 22 tests passed；最终主线程验证 compileall exit 0，make test 191 tests passed，git diff --check main..HEAD exit 0。

Review

subagent review 的 Findings 为 None。它确认本 PR 没有强制 answer_only，没有强制外层搜索，没有触碰 runtime，且 notes.md 与 fact pack 边界符合设计。

残余风险

新增测试是文档契约字符串测试，不是自然语言语义解析器。它能防止关键短语和显式口径回退，但不能证明所有同义错误措辞都会被捕获。这个风险在 docs/Skill-only PR 中可接受；如果未来输入泄露再次发生，再考虑更重的 CLI classifier 或运行前 lint。
